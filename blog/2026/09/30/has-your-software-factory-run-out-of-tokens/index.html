Has Your Software Factory Run Out of Tokens?

By Max Barrass · 6 min read

I was getting a good run going with my personal software factory when I ran out of tokens. Back then, I did not understand token resets or how to plan around them.

My factory runs across two laptops and two PCs, with multiple agents and subagents and work continuing around the clock. When the next change stops moving, capacity is a very real question.

I have built it with off-the-shelf tools you can use too. The architecture connecting them is what makes the capacity question interesting: which part of the factory needs attention?

With four or five projects running at once, I have repeatedly exhausted my available AI allowances over a short period and used the resets provided with that access. Capacity is a practical concern in my own setup.

I went through about three iterations, with earlier token gaps as well. A month and a bit into the process, I still ran out of tokens amid an otherwise good run. Learning about resets and learning to plan around them were part of building the factory.

I tried filling those gaps with other paid models, but switching broke my flow. More capacity was not the same as continuity in my work.

The holes I have pointed out in my contribution graph are interruptions when I ran out of tokens. I can explain those pauses from my own experience; the graph alone cannot. I still check the working records for allowance limits, review delays and failed dependencies before deciding what to change.

The useful management question is broader: what capacity does the next accepted change require, and which part of that capacity is unavailable?

Look at the queues before buying more capacity

A factory can have plenty of model access and still be unable to deliver.

There may be five changes waiting for one person to review them. A pipeline may be failing on the integration branch. The next issue may contain three incompatible interpretations of the desired behaviour. An external decision may be blocking a migration.

Each needs a different response. More implementation activity can make a review bottleneck worse by enlarging the pile of unfinished work. More retries can consume an allowance while leaving the missing decision untouched.

In my setup, each project has a coordinating agent and implementation subagents. GitHub issues track the work; pull requests are reviewed, with automated tests and deployment pipelines. That arrangement gives me places to inspect when something waits. You can design the same visibility into your own factory.

That gives a capacity discussion something concrete to work with.

Treat model access as a planned dependency

I use VibeGov as policies for ChatGPT to follow, including accountable delivery and continuity. My local Forgejo server supports private work and deployments; GitHub supports public work and pipelines. Keeping those roles clear helps me reason about where capacity is needed.

That means understanding the available allowance, the relevant renewal window, the authorised spending boundary and the work that depends on them. It also means recognising that different tasks need different amounts of context, reasoning, tool access and verification.

A small documentation correction should not automatically inherit the same execution plan as an uncertain architectural investigation. Choose an approach proportionate to the work. Review whether repeated context loading, unfocused exploration or avoidable retries are consuming capacity without improving the result.

I am making this open-source framework repeatable. Recording capacity decisions and recovery patterns gives me reusable knowledge to carry between projects, rather than working out the same arrangements each time.

Give the queue a budget and an owner

A prioritised backlog becomes more useful when its ordering reflects the capacity actually available.

Identify the work needed to keep the system healthy, the changes with an immediate delivery obligation and the experiments that can wait. Keep space for validation and repair. Allocating the entire allowance to generating implementation leaves the factory vulnerable when the final check finds a defect.

Name the person who can change priorities when capacity tightens. Otherwise, every contributor may decide their own task is the exception worth starting, and the organisation inherits several partly completed changes.

A modest operating record can cover the task, its owner, the expected checks, a spending or execution boundary and the next decision point. Review estimates against actual use. Improve them as evidence accumulates rather than presenting the first guess as a precise forecast.

Checkpoint before the work becomes stranded

A capacity limit is much easier to handle when the next contributor can see what has already been established.

Before a session stops, record the repository state, last verified result, uncommitted work, remaining acceptance criteria and reason progress paused. Include how to repeat important checks. As I improve the shared foundation, I want agents to use consistent handoff conventions while retaining each project's specific evidence.

Do not use the checkpoint to turn an attempt into a completion claim. A change may be implemented but awaiting review. A test may pass locally while the integrated result remains unknown. Those distinctions determine the next safe action.

When permitted capacity is exhausted, pause the affected execution until access renews, or use an explicitly approved alternative within its terms, permissions and budget. Preserve the work so recovery does not depend on reconstructing an expired conversation.

Stop funding the same failed attempt

Some interruptions deserve investigation before another run starts.

Repeatedly applying equivalent changes to the same failure can create a loop that is both expensive and difficult to unwind. VibeGov’s recovery guidance uses a circuit-breaker approach: preserve the acceptance criteria, retain the last verified state and require a material change in evidence or approach before resuming a failing work unit.

Apply the same discipline to a broken pipeline or an unresolved dependency. Decide what must change, who owns that change and which independent work remains authorised. A blocked migration need not suspend an unrelated, ready documentation correction.

Measure the capacity that produces acceptance

I want to compare usage, waiting time, failed checks and accepted changes across similar tasks. Those outputs help explain how work moves. Observing the outcome requires another question: did the resulting software serve its intended purpose? Recording both gives me a basis for improving the method.

On my tiny budget, continuity matters to the ideas I want to pursue. I want project lessons to improve the foundation, so an interruption needs less reconstruction and an idea need not be put aside indefinitely.

If you try this shared approach, record where your factory stops and how it resumes. Which checkpoint helped? What context was missing? I am curious how others handle this with their resources. Share the conventions you reuse and the outcomes you observe; those findings can help newcomers and experienced builders alike.
