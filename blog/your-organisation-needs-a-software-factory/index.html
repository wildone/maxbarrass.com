Building the method

Your Organisation Needs a Software Factory. Here’s How to Build One.

By Max Barrass · 5 min read

  • Give each work unit boundaries and a destination

  • Related reading

I am building a repeatable framework for how I work: two laptops, two PCs, multiple agents and subagents, with four or five projects running concurrently and work continuing around the clock. I call the arrangement my software factory.

The ingredients are off-the-shelf tools you can use too. I use ChatGPT, GitHub issues and pull requests, automated tests and deployment pipelines. I also run a local Forgejo server for private work and deployments, with GitHub for public work and pipelines.

What makes this a factory is how I connect the work: an idea becomes an issue, an agent coordinates implementation, and the resulting change goes through review and verification. I remain responsible for the decisions.

I want room to pursue ideas that would otherwise stay on the backburner. A repeatable foundation helps me work towards that. Imagine what you could try personally or in your business. Here is where I would begin.

Start with an outcome someone owns

Choose one recurring problem. Perhaps staff cannot complete a request without copying information between systems. Define whose work should improve, what currently fails and what an acceptable result would look like.

Keep the first increment small enough to assess. “Improve operations with AI” gives a team almost no basis for deciding whether it has finished. “Let the service team submit this request once, with the required checks and a visible outcome” creates something people can inspect.

Name a human accountable for the intended result. Give that person a route to the people who understand the work, its risks and the systems it touches. A factory needs someone able to decide that a beautifully implemented request was the wrong request.

Make the work ready before allocating agents

An idea can enter the backlog as a sentence. Before implementation, it needs enough definition to prevent different contributors building different answers.

Record the expected behaviour, scope, acceptance criteria, dependencies and verification approach. Link to the relevant requirement. If the requirement is missing or contradictory, make resolving that gap an explicit task.

I use GitHub issues to make work trackable. VibeGov supplies policies I ask ChatGPT to follow: clarify the assignment, preserve ownership and bring back evidence. It is the governance I use to keep delivery accountable. The tools and pipelines do the execution.

Consider a request form. What happens when required information is absent? Who may submit it? Can someone save it and return later? How is a failed submission recovered? Those questions are cheaper to expose while defining the change than after several agents have implemented incompatible assumptions.

Give each work unit boundaries and a destination

An agent needs a bounded assignment: the relevant context, the permitted changes, the checks to run and the evidence to return. Give it a clear route for questions and a stopping condition when progress becomes unreliable.

In my setup, each project has a coordinating agent and subagents doing implementation. That gives me somewhere to look for ownership, overlapping changes and the next integration decision. I want specialist help where the work needs it, with a clear assignment and a result that can be reviewed.

I am progressively extracting reusable knowledge, patterns, policies, components and tooling into an open-source foundation. The aim is consistent conventions and workflows for agents, so the next project can reuse what fits. Each project's lessons can improve that foundation.

Budget for verification and integration

A fast builder can overwhelm a slow reviewer. Plan the review capacity alongside the implementation capacity.

Tie tests to intended behaviour and the failures worth catching. For the request form, that might mean checking valid submission, invalid input, permission boundaries, saved state and recovery after a failed request. Choose the testing layers the risk warrants. A small internal correction and a change to a critical service need different amounts of evidence.

Someone must also own the path back into a healthy shared codebase. A completed branch can still be incompatible with changes made elsewhere. Check the integrated state, the build and the resulting user behaviour before making a release claim.

Keep the release record useful: what changed, what was checked, what remains uncertain, how to reverse the change where needed and who accepts the residual risk.

Connect the factory to the organisation

I have to answer a question that gets larger inside a business: who gives an agent authority, and how does everyone understand its limits? Governance.Foundation's wider work helps frame that question.

The factory needs legitimate sources of context, appropriate access and clear decision rights. An agent permitted to repair a form should not infer permission to change retention rules, disclose customer data or redesign another team’s service.

Make exceptions visible. When a decision blocks one part of the work, identify that dependency and continue only with independent, authorised work. When an experiment produces a useful finding, turn it into a requirement, issue or recorded decision that the next contributor can find.

Build the first working loop

Start with one service and one small delivery queue. Agree what makes work ready, what counts as accepted evidence and who can authorise release. Run a bounded increment through the complete route, then examine where it waited, failed or required somebody to reconstruct missing context.

Improve that route before multiplying it. I want to observe outputs, such as accepted changes and corrections, alongside outcomes: did the software improve the task it was built for? Keeping those questions separate helps me learn what to change next.

This is how I work on my tiny budget. The framework is evolving as I learn what to reuse. Begin with a practical test: can you follow one idea to an accepted result and understand the decisions?

Try a small loop with this shared approach. Which outputs can you verify, what outcome were you seeking, and what belongs in a reusable foundation? I wonder what others are doing with their resources. Share how your loop works so we can learn from each other's attempts.
